# DICE：CoC 7 数值检定设计

日期：2026-09-19。状态：已实现，验收见第 10 节；未提交、未推送。

## 1. 终态与范围

**通用 RP 保留现有 D20；CoC 人物使用 CoC 第七版检定。模型提供数据，程序掷骰并裁定，模型按结果续写。**

两种规则由用户明确选择，不通过某次请求是否漏填数值来猜测。CoC 请求缺数值时不编造、不随机生成阈值，也不偷偷回退 D20。

本期的 CoC 支持范围：

- 单项技能／属性检定。
- 奖励骰与惩罚骰。
- 普通双方对抗。
- 近战攻击对闪避、近战攻击对反击的命中裁定。

不实现完整跑团引擎：本期不处理建卡、属性编辑与更新、联合检定、多人协作、战技及体格差、伤害与护甲、HP／SAN 扣减、战斗轮、枪械连射与弹药、孤注一掷、幸运消耗、成长或追逐系统。未支持的规则不以自定义综合分代替，也不伪装成已支持的检定。

D20 的概率、标准／积极两档及现有行为仍以[现行设计第 1、2.1 节](./dice-app-target-design.md)为准，不在这里重抄规则表。随机遭遇不在本次改造范围。

## 2. 规则选择与数值来源

### 2.1 设置

在现有行动检定开关下增加规则选择：`d20` / `coc7`，默认 `d20`，不改变现有用户的玩法。

设置归 Dice 所有，与当前开关和频率同存于全局 `xiaobaiOs.apps.dice`，不新建聊天分区。它是用户长期偏好，不是运行状态；关闭玩法不重置选择，清除 Dice 全局设置时删除。保存确认后生效，失败继续使用已确认值。当前设置所有权见 [types.ts](../apps/dice/types.ts:5) 与 [settings.ts](../apps/dice/settings.ts:8)。

标准／积极选择只作用于 D20。CoC 使用原版的检定时机：有需要裁定的不确定性与失败后果，且行动确实可以尝试；已经确定、没有实际阻力或根本不可能的行动不为了掷骰而制造不确定性。切回 D20 时保留原频率偏好。

每次模型生成开始时捕获规则选择；规则在该请求返回前改变，则旧运行失效，不能拿新协议解析旧响应。UI 在现有生成／检定占用期间禁止切换规则，不增加持久锁。已应用结果不因设置改变而删除或改判；历史、同楼结果注入及显式重试按记录自身规则解释，只有新检定读取当前选择。

### 2.2 模型填数

CoC 的 `value` 是当前上下文已经确立的完整技能／属性数值，尚未取半、取五分之一；人物卡、世界书或前文更新均可能提供该事实。

- 优先选择该行动在 CoC 中适用的技能，没有适用技能时再使用合适属性。例如攀墙通常使用“攀爬”，不是统一使用“敏捷”。
- 有当前数值就原样填写，不把受伤、环境等因素临时拍成一个新数值；适用的奖惩条件单独表达。
- 已明确是未受训练的技能，可以依据已知的原版基础值；未知人物数值不等于未受训练。
- 没有必要数据就先补充数据，不发缺字段的请求，不自动建卡或随机填数。
- 不设 `max`，不把 DnD、五级制等其他体系换算成 CoC 百分比，也不将多个数值加权成“综合战力”。

程序校验请求结构和数值形状，不声称能独立验证模型是否忠实抄取人物卡。抄数准确性属于真实模型验收。

### 2.3 小白酒馆只作结构参考

小白酒馆由程序按人物与属性名查状态栏，见 [action-checks.ts](../../tavern/shared/action-checks.ts:220)；DICE 改由模型提交数值。两者都可以分为“获得检定依据 → 裁定 → 展示及续写”。

酒馆现有数值算法使用状态栏区间归一化、难度加减偏移和固定临界区间，并非 CoC；相关实现见同文件的 `resolveStatusGaugeBasis`、`resolveStatusGaugeOutcome` 与 `executeTavernActionCheck`。本期不导入或修改这套算法，不伪造状态栏调用它，不改酒馆的数据库、工具循环、事件格式或卡片。

CoC 规则留在 DICE 的领域层。当前没有第二个采用同一规则的实际消费者，因此不新增跨 APP 通用检定框架。

## 3. 请求协议

继续使用现有 Tagged JSON 运输方式；标签、末尾停止、Markdown 保护及消息标记契约引用[现行设计第 5.1、5.3 节](./dice-app-target-design.md)，不增加原生工具调用或另一个模型请求。

D20 保持原请求格式。CoC 使用以下结构化字段；字段名是程序接口，不改变 CoC 规则。

| 字段 | 要求 | 语义 |
| --- | --- | --- |
| `kind` | 必填 | `skill`、`opposed`、`melee_dodge`、`melee_fight_back` |
| `action` | 必填 | 本次尝试及其目标 |
| `character` | 可选 | 行动者；近战时根对象始终代表主动攻击者 |
| `stat` | 必填 | 行动者采用的技能／属性名称 |
| `value` | 必填 | 对应完整数值 |
| `difficulty` | 仅 `skill` 必填 | `regular`、`hard`、`extreme`；双人检定不提供此字段 |
| `bonus`、`penalty` | 可选，缺省为 0 | 行动者适用的奖励骰／惩罚骰数量 |
| `opponent` | 三种双人检定必填 | 对方的 `character`、`stat`、`value`，以及可选的 `bonus`、`penalty`；前三项必填 |
| `stakes` | 可选 | 成败后果及不受结果改变的既定事实 |

`opponent` 采用与行动者相同的数值／奖惩字段定义，不另造一套 `target_value`、`target_max` 或对方难度规则。

字段校验由一个契约定义派生解析和模型字段说明：

- 字符串必须非空，已有字段长度沿用 [ACTION_CHECK_REQUEST_FIELDS](../apps/dice/domain/action-check.ts:22)，对方相同字段复用同一定义。
- 本期自动执行接口接受正的安全整数 `value`；不把字符串转数字，不截断到 100。CoC 确实存在超过 100 的属性，是否允许该场景检定仍受原版情境与人类极限规则约束；未实现的专门程序不由普通对抗代替。零值请求不执行，而不是送入幸运兜底。
- 奖惩骰为非负安全整数，先相互抵消。本期接口支持抵消后的净数量 0、1、2；更复杂情况明确不支持，不静默截断或自行抬难度。这是本期覆盖范围，不宣称是所有 CoC 子规则的统一上限。
- `skill` 不接受 `opponent`；双人检定不接受缺失的对方数据；未知字段、骰值、结果、任意阈值等不进入请求。
- 整个请求、两方数据、目标消息及次数上限均验证通过后，才调用随机源。格式错误不会掷出“半次对抗”，也不会自动调用模型修 JSON。

可执行示例定义于 [CoC 模型契约](../apps/dice/protocol/coc7-contract.ts)，由 [CoC 测试](../tests/dice-coc7.test.js) 通过正式标签解析与检定准备入口执行，不在本文复制第二份示例。

## 4. CoC 裁定规则

### 4.1 单项检定

设完整数值为 `V`，实际骰值为 `R`，所有除法向下取整。

| 所需成功程度 | 本次成功阈值 T |
| --- | --- |
| `regular` | V |
| `hard` | ⌊V / 2⌋ |
| `extreme` | ⌊V / 5⌋ |

临界规则优先：

- `R = 1` 为大成功。
- `R = 100` 为大失败；若本次成功阈值 `T < 50`，`R = 96–100` 都是大失败。
- 其余结果相对于完整 `V` 判断极难、困难、普通成功或失败，再比较是否达到本次所需程度。

因此“骰子的成功等级”和“本次行动是否达成”是两个不同事实。数值 65、要求困难：骰值 27 是困难成功并达成；骰值 43 虽属普通成功等级，却未达成本次目标。不能为了显示绿色成功而放行后者。

没有“简单乘 1.5”或“几乎不可能固定 5%”档位，也不重复按人物强弱调整已经含有人物能力的数值。任务、做法、环境的判定采用原版难度与奖惩机制，不为同一理由重复给予优势或惩罚。

依据：[R1] 的难度及取半／取五分之一表，[R3] 的大失败阈值规则。

### 4.2 百分骰与奖惩骰

程序产生一个个位骰和一个基础十位骰；每个有效奖惩骰增加一个十位骰，共用个位。每个组合先按百分骰解释为 1–100，再选取：奖励取最低，惩罚取最高。`00` 十位与 `0` 个位的组合是 100，其余 `00` 十位组合是 1–9。

这不能改成多个独立 D100 取最小／最大。例如个位为 0、十位候选为 00 和 10，候选结果为 100 和 10；奖励取 10，惩罚取 100。临界判定使用最终选中的结果。

骰面采样与结果选择只发生一次；显示动画不采样，重试不重新选择十位骰。依据：[R1]。

### 4.3 普通双方对抗

`kind = opposed`。双方各用自己的完整数值及奖惩骰掷一次，依据各自数值判断等级，不先套同一个任务难度。

按大成功、极难成功、困难成功、普通成功、未成功比较；未成功保留普通失败／大失败的区别供后果叙述，不擅自把失败解释成已经完成某个单方任务。对抗中临界失败范围以该方完整数值的 50 分界判定。

同等级时，完整技能／属性值高的一方占优，而不是比较折算阈值或原始骰点。等级与数值均相同，按核心规则允许的处理返回僵持；不擅自判防守方胜，不自动连掷直到出现赢家。这里选择的是原规则允许的僵持分支，不采用入门规则另行重掷较低者胜的流程。依据：[R4] 的 Opposed Rolls 原书摘要；两种公开说明的差异见资料边界。

对抗胜负是相对裁定，不等同于某方取得普通成功。双方均未成功时仍依上述对抗比较规则处理并保留各自失败事实，不能拿这个结果额外宣称成功开锁、造成伤害等未裁定后果。近战有单独的双方失败规则，见下一节。

用于验收的例子：

| 甲力量 20 的骰值 | 乙力量 40 的骰值 | 裁定 |
| --- | --- | --- |
| 15：普通成功 | 60：失败 | 甲胜 |
| 15：普通成功 | 30：普通成功 | 同级比较完整数值，乙胜 |
| 3：极难成功 | 12：困难成功 | 甲胜 |

高数值更容易取得好等级，且同级占优，但不是必胜。模型仍须先判断情境可否形成有效对抗，不让一个规则上不可能的尝试靠随机骰获得资格。

并非出现 NPC 就一定双方掷骰。CoC 也允许用 NPC 的对抗能力确定一次单项检定的难度；是否采用这一程序由守秘人按原规则判断，不能既用对方能力提高单项难度，又为同一目标额外进行双人对抗。本期 `skill` 接受守秘人已选好的难度，不新增另一套 NPC 阈值计算器。

### 4.4 近战命中对抗

根对象为主动攻击者，`opponent` 为被攻击者。攻击者使用适用的格斗技能；对方分别使用闪避或适用的格斗技能。

| `kind` | 裁定 |
| --- | --- |
| `melee_dodge` | 攻击者须取得更高成功等级才能命中；同成功等级由闪避方占优 |
| `melee_fight_back` | 更高成功等级的一方命中；同成功等级由主动攻击者占优 |

双方均未成功时，先返回无人命中，不再套用平局优先规则。近战平局不比较谁的面板数值更大。大失败事实仍保留，由模型落实适当后果，不能自行增加一个未获规则支持的命中。

结果只裁定本次命中、反击命中、闪避或无人命中，不掷伤害、不扣 HP、不管理轮次，也不把极难攻击和反击解释成相同伤害。枪械不是这两种近战对抗。依据：[R2]、[R4] 的近战摘要。

## 5. 结果、卡片与提示词

### 5.1 同一份裁定数据

一次执行返回一个包含完整依据和结论的结果：

- 原请求中的行动、参与者、技能及数值，保留原位置，不复制到另一份人物档案。
- 程序确定的规则身份、实际骰面、最终骰值、使用的阈值、成功等级，以及达标／对抗／命中裁定。
- 对抗时两方的结果和总体裁定放在同一条记录内。

卡片与续写从同一条结果投影，不能分别再计算一次胜负。历史裁定是当时已经发生的事实，不根据今天的设置或算法重新改判。

### 5.2 卡片内容

D20 保持现状。CoC 单项卡显示人物／技能原值、所需难度和阈值、最终骰值、等级与达成状态；例如“普通成功等级但未达到困难要求”必须清楚区分。

对抗卡显示双方数值、骰值、等级及总体胜负／僵持／命中结论。存在奖惩骰时允许查看候选骰面及最终选择；不用颜色代替文字，不增加重掷按钮。CoC 使用百分骰语义，不能仍画一个标着 100 的 D20。

当前卡片入口见 [check-card.ts](../apps/dice/ui/check-card.ts:13)。视觉沿用现有聊天附属卡与揭晓生命周期，不建立独立历史页、骰子桌或第二套 UI 状态。

### 5.3 写给模型的内容

沿用现有 Prompt 分层，见 [prompt.ts](../apps/dice/protocol/prompt.ts:31)：

1. 领域说明：当前规则、支持的检定范围、情境判断与数值取用职责。
2. 契约：仅当前规则的字段含义、必填条件和 Tagged JSON 的调用时机，由协议定义生成。
3. 结果资料：当前候选中仍被正文标记引用的已确定结果；资料明确区分成功等级和行动是否达成。
4. 续写边界：结果作为既定事实，通过场景中的行动与后果表现；骰点、规则、调用过程不成为剧情旁白或角色台词。

不同时注入 D20 和 CoC 的两套新请求说明，不靠追加几句与旧规则互相覆盖。CoC 的稳定计算由代码完成；提示词不是整本规则书，也不假定仅写“按 CoC”就能省略接口和支持范围。未实现的特殊规则不让模型用近似参数冒充。

模型可以做守秘人的情境裁量，但不能代替程序掷骰、决定胜负、自动消费幸运点或自动发起孤注一掷。继续使用原角色身份、文风和用户预设，不增加独立裁判 Agent。

## 6. 运行与保存：沿用现有闭环

宿主收尾、同步应用、揭晓、原生续写和正常保存引用[现行设计第 4.3 节](./dice-app-target-design.md)；停止、编辑、切聊、切候选、标记移动／删除／插回引用同文第 5.3 节。它们是两种规则共用的执行约束，不在 CoC 中再建一条运行链。

CoC 新增的边界：

- 一次双人对抗属于一次检定，占用一条记录、一个正文标记和一次自动续写，不按双方或奖惩骰拆成多次。
- 两方结果准备完成后一次性应用；应用前再次核验目标。不能先显示一方，再在等待另一方时让用户看到可重掷状态。
- 现有单候选八次上限按完整历史记录累计，D20 与 CoC 共用，不因切规则、删除标记、失败重试清零。
- 续写失败或用户停止后，沿用整次对抗的全部骰面及裁定，不重掷任何一方、不重播揭晓。已有部分后文时不自动重放整段。
- 软件请求重试不是 CoC 的孤注一掷；本期不实现后者。
- 新楼不注入前楼骰点数据，依靠已生成的叙事正文承接。

CoC 不新增专用聊天保存、服务器读回、补存、缓存或刷新恢复任务。宿主正常保存前离页导致未保存结果丢失的既有取舍不变。用户主动清理消息数据时，仍走已有明确保存删除结果的路径。

## 7. 数据与代码所有权

### 7.1 最少持久化数据

| 数据 | 所有者／位置 | 必须持久化的原因 | 生命周期、失败与删除 |
| --- | --- | --- | --- |
| 规则选择 | DiceSettings，现有 OS 全局设置 | 用户长期玩法偏好 | 按第 2.1 节的确认保存与清理规则 |
| 已执行检定依据及结果 | 当前消息／候选的 `extra.xiaobaiOsDice` | 同楼失败重试、宿主保存后的历史及跨设备卡片必须保留原结果 | 跟随消息／候选；应用后不回滚，落盘取舍见第 6 节；显式清理删除自有记录和标记 |

规则身份是每次历史检定的一部分，不是将全局设置镜像到聊天。记录采用可区分 D20／CoC 的当前联合模型；不让 `roll=15` 或一个 `dc` 字段同时承担两种相反的含义。

正式线 D20 旧记录在加载／导入入口一次性转换：保留 ID、请求、骰点、当时 DC 与已确定结果，不按 CoC 重算。既有正式线 v1 格式和样本见 [records-v1.ts](../apps/dice/storage/records-v1.ts) 与 [真实 fixture](../tests/fixtures/dice-message-a32c28d0.json)。本次通过 `git ls-remote upstream refs/heads/main` 确认正式线仍为 `a32c28d0518ce1e870ba0b0935a2b149438b465a`。

当前联合记录继续使用测试线 v2：D20 记录增加 `rule: d20`；CoC 记录为 `id / rule: coc7 / request / result`，其中 `result` 保留双方骰面与总体裁定。类型与读取入口唯一来源为 [check-records.ts](../apps/dice/domain/check-records.ts)。没有为未进正式线的旧 v2 无规则字段格式增加兼容分支；运行只接收当前模型或由正式线 v1 转换来的数据，不额外迁移小白酒馆数据。

运行 token、捕获的规则、取消、错误、动画、待续写和待注入 Prompt 都只在内存。没有新数据库、状态栏分区、属性缓存、持久化进行中标记或胜负统计。

### 7.2 职责与入口

| 层 | 本期职责 |

## 8. 实施顺序与验收

### 实施顺序

1. 依据本稿冻结受支持的规则、请求和结果结构，确认现行正式线记录样本；不先铺 UI 或另造运行框架。
2. 在 Dice 领域层实现 CoC 规则与最少确定性测试；D20 算法保持不变。
3. 接入解析、结果记录、按规则生成的模型契约及投影；模型示例以正式解析 fixture 为来源。
4. 接入现有设置、取消保护、单次应用、卡片和续写链；不得引回检定专用保存。
5. 完成集成、浏览器及构建验收后更新交付状态。真实付费模型测试需另有授权，不拿模拟供应商证明模型抄数和叙事质量。

### 最少必要检查

| 层 | 稳定契约与真实故障 |
| --- | --- |

| 骰面单测 | 奖惩抵消、共用个位、00+0=100、选择后再判等级；不以随机抽样统计代替枚举或确定样本 |

## 10. 实现与验收记录

- 领域规则：[coc7.ts](../apps/dice/domain/coc7.ts) 负责百分骰、奖惩骰、等级和四种裁定；[coc7-request.ts](../apps/dice/domain/coc7-request.ts) 负责数值与条件字段校验。CoC 未收到有效数值不会采样或回退 D20。
- 提示词按已选规则生成一套请求说明，结果按自身规则投影。各 `kind` 的条件字段、必填性及对方字段定义由 `COC7_REQUEST_VARIANTS` 同时驱动解析与说明，模型契约明确列出该类型必须省略的条件字段。嵌套结果仅在 JSON 字符串内转义酒馆宏，保留结构括号和完整骰面数据；续写继续使用共用反元叙述边界。
- 运行复用现有会话、消息与候选同步、揭晓、原生继续及宿主正常保存。规则偏好确认保存后取消旧运行；忙碌状态从宿主与现有运行推导，不保存锁。
- 卡片复用同一揭晓与恢复生命周期。CoC 百分骰显示单方或双方数据，奖惩明细可展开，单项达标状态与成功等级分列。长名称不在卡头重复一遍。
