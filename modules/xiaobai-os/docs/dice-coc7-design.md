# DICE：CoC 7 全局玩家面板与单项检定设计

日期：2026-09-19。状态：全局面板与单项检定已实现，本稿验收见第 10 节；未提交、未推送，未进行真实模型验收。本稿替换先前的 CoC 设计。

## 1. 终态与范围

**玩家拥有一份全局能力面板；用户一键随机生成，也可手调。AI 只选择技能／属性和难度，程序查值、掷骰、裁定，AI 按结果续写。**

面板不绑定角色卡、用户角色或聊天。新聊天、换卡和刷新不会丢失或重新随机属性。用户无需维护 NPC 数值，AI 不从正文、角色卡或世界书抄取检定值，也不因缺数值向用户追问。

本期是采用 CoC 7 百分骰规则的简化 RP 检定，不是完整跑团引擎：

- 支持玩家的单项技能、属性和幸运检定。
- NPC 的阻力体现为玩家检定的难度；纯 NPC 行动由叙事处理，不借用玩家面板掷骰。
- 不支持双方对抗、近战闪避／反击对抗、奖励／惩罚骰、完整职业建卡、伤害与护甲、当前 HP／SAN／MP 管理、战斗轮、幸运消耗、孤注一掷、成长或追逐。

D20 的规则、标准／积极两档与共用运行生命周期仍以[Dice 总设计](./dice-app-target-design.md)为准。随机遭遇不在本次改造范围。

## 2. 全局玩家面板

### 2.1 使用范围与唯一事实来源

继续使用全局 `xiaobaiOs.apps.dice` 设置仓库。规则选择与玩家面板均归 Dice 所有，不增加数据库、聊天分区或角色绑定。

“全局”指当前 SillyTavern 用户设置范围，不承诺不同独立实例之间自动同步。关闭行动检定、切回 D20、换卡或换聊天均保留面板；只有用户主动生成、编辑或清空才改变它。剧情描述和模型请求无权覆盖面板。

保存基础属性、幸运及技能训练增量；技能基础值、最终技能值和衍生参考值由这些事实计算，不另存一份可漂移的最终值。

### 2.2 能力目录

Dice 领域层维护唯一能力目录：稳定 ID、显示名称、分类、适用行动、基础值或派生规则。UI、请求校验、面板查值和模型可选能力说明共同消费此目录，不分别维护同名映射表。

基础属性为力量 STR、体质 CON、体型 SIZ、敏捷 DEX、外貌 APP、智力 INT、意志 POW、教育 EDU；幸运是独立能力，不混为第九项基础属性。

首版采用固定常用技能集，清单、稳定 ID、名称和适用范围唯一维护于[能力目录](../apps/dice/domain/coc7-catalog.ts)。不增加自定义技能编辑器或职业管理。

技能基础值已核对第 10 节的标准 CoC7 角色表后写入目录，本文不复制数表。例如闪避基础值为 `floor(DEX / 2)`，敏捷变化后据此重新派生，训练增量不变。目录外的专长不能靠名称猜测或临时造数接入；没有合适技能时，只有确实适用的属性才能承担检定。

### 2.3 一键随机

初始化完全由本地程序完成，不请求模型：

| 项目 | 初始生成方式 |
| --- | --- |
| STR、CON、DEX、APP、POW | 各自掷 3D6 × 5 |
| SIZ、INT、EDU | 各自掷 (2D6 + 6) × 5 |
| 幸运 | 独立掷 3D6 × 5 |
| 技能 | 目录基础值，加下述随机训练增量 |

从技能目录中随机选择八个不同技能，分别分配 `40、30、30、20、20、20、10、10` 的训练增量，其他技能训练增量为零。生成后即有一份完整可用面板，不要求用户再走职业和兴趣点分配流程。

**技能分配是本插件的快捷初始化方案，不冒充 CoC 完整职业／兴趣点建卡。** 本期不增加年龄修正或完整建卡流程。

用户看到并编辑最终技能值；程序用“最终值减当前基础值”得到训练增量。最终值低于基础值时明确报错，不静默截断。修改属性后，关联技能基础值随之更新，已保存训练增量保留。

### 2.4 衍生值与数据校验

展示以下只读参考值，不重复保存：

- HP 上限：`floor((CON + SIZ) / 10)`。
- MP 上限：`floor(POW / 5)`。
- 初始 SAN：POW。

必须标为“上限／初始”，不能伪装成当前资源；它们不进入可检定能力目录。本期没有扣血、扣理智或恢复资源的状态链。

属性与幸运要求正的安全整数，训练增量要求非负安全整数；完整面板及其派生结果都须有效。使用面板与保存替换值时复用领域校验，不把字符串强转数字、不自动截断为 100、不用随机值修补缺项。初始化范围不等于手调硬上限。验证失败明确报告，不能破坏上一份已保存面板。

全局设置加载保留面板原始内容；Dice 将其投影为未建立、可用或损坏三种临时读取状态，不另存错误标记。损坏面板不能进入检定计算，但不能阻断 OS 初始化或其他设置读写；只有用户确认清空或成功保存替换面板才移除原数据。

## 3. 初始化与手调界面

在现有行动检定设置中保留 D20／CoC 规则选择。选中 CoC 后显示“我的属性”区域；标准／积极只属于 D20，切换规则不清除原频率偏好。

| 状态 | 用户可见操作与结果 |
| --- | --- |
| 无面板 | 显示“待生成属性”与“一键随机”；生成完整面板并保存，成功后可直接使用 |
| 已有面板 | 紧凑展示八项属性、幸运及只读衍生值；技能分组展开，点击数值进入手调 |
| 编辑中 | 在内存草稿中调整数值或重新随机；保存才替换正式面板，取消不影响原面板 |
| 保存失败 | 保留草稿和旧的已确认设置，显示可重试错误；重试保存不得再次随机 |
| 面板损坏 | 即使关闭行动检定或选中 D20，也显示损坏提示及清空／生成替换面板入口；替换先产生草稿，保存前保留原始数据 |
| 清空属性 | 明确确认后只删除全局面板，不删除聊天、骰子历史或规则偏好；失败保留原面板 |

首次随机得到的候选在保存完成前同样是草稿。没有旧面板且保存失败时，仍处于未初始化状态，候选留在当前编辑过程供重试。

编辑数值时 Esc 仅取消当前输入并消费该按键事件；此前的草稿修改保留，不触发 OS 外壳返回。

不要求姓名、职业、背景或身份绑定，不增加 NPC 页面、多角色列表、第二个管理 APP。界面文案归表达层集中定义，代码与测试不通过文案识别状态。窄屏、键盘和主题适配使用现有 UI 边界，不用密集表单或大量解释代替清晰操作。

## 4. 模型请求与提示词

### 4.1 最小请求

继续使用现有 Tagged JSON 运输、末尾停止、Markdown 保护及正文标记契约，见[Dice 总设计](./dice-app-target-design.md)。不增加原生工具调用、独立裁判 Agent 或另一条模型请求。

CoC 请求只有三个必填字段：

| 字段 | 含义 |
| --- | --- |
| `action` | 一句本次尝试及目标，用于上下文与展示，不附带额外机制 |
| `stat` | 能力目录中的稳定 ID，选择一个技能、属性或幸运 |
| `difficulty` | `regular`、`hard`、`extreme` |

模型在机制上只做两项选择：**检定什么能力、要求什么难度**。行动者固定为全局面板所属玩家，不要求模型反复声明身份。

删除旧 CoC 请求的 `kind`、`character`、`value`、`opponent`、`bonus`、`penalty`、`stakes`。不保留“模型填数”和“程序查值”并存的入口。

请求字段由一个契约定义同时驱动解析与字段说明；`action` 沿用现有长度约束，`stat` 的有效集合来自能力目录。未知字段、未知能力、非法难度均明确拒绝，不猜别名、不调用模型修补 JSON。

可执行示例由实现阶段的模型契约持有，并通过正式解析、面板查值和执行入口测试；本文不另存一份未经执行验证的模型调用样例。

### 4.2 提示词的职责顺序

提示词以一个清晰的正向流程说明职责，不把旧提示词保留后再追加互相覆盖的禁令：

1. 说明程序已管理玩家属性，提供可选能力的 ID、名称及适用行动；不要求模型掌握或回填面板数字。
2. 玩家尝试确实可行，但结果不确定且失败有实际后果时才检定。同一目标不为每个动作碎片连续掷骰；新目标或新障碍才重新判断。
3. 优先选合适技能，没有适用技能时才选合适属性；幸运用于机会本身的偶然性。难度反映目标与阻力，不能因为玩家数值低再加一次难度。
4. 叙述尝试，提交请求，停在结果出现之前；收到程序结果后按既定裁定续写，保持角色与文风。

NPC 造成的阻力由情境难度表达，不要求用户录入 NPC，也不临时生成 NPC 属性。纯 NPC 行动不发玩家检定。这是本期的简化 RP 边界，不宣称等价于完整 CoC 对抗或战斗。

CoC 固定采用以上检定时机，不设置每回合骰子配额，不沿用 D20 的积极档。模型返回结果后的叙事边界沿用共用协议，不把骰点、字段或调用过程写成角色台词。

### 4.3 尚未初始化

没有有效面板时，不注入可发起新 CoC 检定的提示词，不执行新 CoC 请求；UI 明确显示待初始化。普通聊天可继续，不追问某项技能数值、不随机补齐、不回退 D20。

历史结果仍可显示，已掷结果的续写重试仍使用原记录；“禁止新检定”不等于“禁止消费已有结果”。损坏面板须报告校验错误，不当作正常首次使用静默处理。

## 5. 程序裁定与展示

校验当前请求、运行有效性、完整面板、能力查值、目标消息与次数限制后，才调用随机源。无效请求不能消耗骰子或留下半条记录。

设查得完整值为 V，骰值为 R：

| 难度 | 本次成功阈值 T |
| --- | --- |
| `regular` | V |
| `hard` | floor(V / 2) |
| `extreme` | floor(V / 5) |

程序生成一个个位骰和一个十位骰，组合为 1–100；00 表示 100。只采样一次，动画与续写重试不重新采样。

保留现有单项检定规则：1 为大成功；100 为大失败，本次成功阈值 T < 50 时，96–100 均为大失败。临界规则优先；其余先依据完整 V 判断成功等级，再判断是否达到所需难度。

成功等级与行动达成是不同事实。例如 V=65、困难要求、骰值 43：属于普通成功等级，但未达到困难要求。卡片与模型结果都必须保留这一差别，不能各自重新判断一次。

结果记录保存本次实际使用的能力 ID、完整值、阈值、骰面、等级和达成结论，以及行动上下文；不复制整张玩家面板。卡片和续写资料从同一条历史结果投影，修改属性后历史结果不重算。卡片采用百分骰语义，不沿用 D20 骰面造型表达 100。

## 6. 运行、快照与保存

宿主收尾、结果应用、揭晓、原生续写及正常保存继续走[Dice 总设计](./dice-app-target-design.md)的共用生命周期，不建立 CoC 专用执行和保存链。

- 每次新回复开始生成时，在内存捕获已确认规则与面板；本次回复及其自动续写共用这一份运行快照。
- 用户中途保存属性或切换规则，只影响下一次新回复；当前运行不得一半使用旧面板、一半使用新面板，也不得拿新规则解析旧请求。
- 运行快照不持久化。停止、切聊、切候选和目标失效继续服从现有取消边界，不保存锁或“进行中”标记。
- 单回复的现有限制引用 `MAX_ACTION_CHECKS`，不在 CoC 定义另一份上限；D20 与 CoC 不因切换或重试重新计数。
- 已掷结果的重试读取原记录，不重新查面板、不重掷、不重播揭晓。软件重试不等于规则上的孤注一掷。
- 刷新后恢复历史续写仍使用原结果；后续真正的新检定按新运行捕获的有效面板处理，不能用今天的数值改写过去。
- 新楼不额外注入前楼骰点，依靠叙事正文承接。

设置只有确认保存成功后才成为有效事实；失败保留旧值及编辑草稿。聊天结果仍由宿主正常保存，未正常保存即离页的既有取舍不变，不新增检定专用补存、读回或刷新恢复任务。

## 7. 所有权与最少状态

### 7.1 持久化与临时态

| 数据 | 所有者与持久化理由 | 生命周期、失败及删除 |
| --- | --- | --- |
| 规则偏好 | Dice 全局设置；用户长期玩法选择 | 关闭功能仍保留，保存失败沿用已确认值；清除 Dice 设置时删除 |
| 玩家属性、幸运、技能训练增量 | Dice 全局设置；跨聊天与重启必须保持的用户事实 | 用户生成／编辑后保存；失败不覆盖旧面板；显式清空属性或清除 Dice 设置时删除 |
| 已执行检定依据与结果 | 消息／候选的 Dice 记录；历史展示和失败续写需要原结果 | 跟随宿主保存；按明确范围清理自有记录及标记，不受清空面板影响 |

编辑草稿、运行快照、取消状态、错误、动画、待续写和待注入提示词仅在内存。技能最终值、HP／MP 上限和初始 SAN 均派生，不增加缓存表、NPC 实体或持久化中间状态。

### 7.2 层与入口

| 位置 | 所有职责 |
| --- | --- |
| `apps/dice/domain` | 能力目录、玩家面板、初始化与校验、派生计算、CoC 裁定及记录不变量 |
| `apps/dice/settings.ts` 与现有 OS 设置仓库 | Dice 定义面板设置；仓库提供业务无关持久化，不接管 CoC 规则 |
| `apps/dice/protocol` | 最小请求契约、解析、模型可选能力说明和结果投影 |
| `apps/dice/application` | 复用会话编排，以运行快照查值、准备并应用一次结果 |
| `apps/dice/host` | 捕获运行配置、宿主事件、消息／候选同步和生命周期适配 |
| `apps/dice/ui` | 规则选择、面板生成与编辑、检定卡片；不维护第二套计算事实 |

复用现有 [production-module.ts](../apps/dice/production-module.ts)、[action-check-session.ts](../apps/dice/application/action-check-session.ts) 和 [message-records.ts](../apps/dice/host/message-records.ts) 入口；不增加 APP 注册、外部依赖、模型 API、NPC 服务或跨 APP 通用框架。不复用小白酒馆语义不同的状态栏算法与存储。

- 清理仅在功能启动／聊天加载边界执行，结果随宿主正常保存；不另发补存请求。实施验收使用测试 fixture，未对用户真实聊天执行清理。

## 9. 实施与验收

实施按以下顺序收敛，不先保留两套协议再逐步打补丁：

1. 核对正式线兼容边界、现有技能基础值资料和旧记录样本；确定能力目录、面板模型、请求及结果契约。
2. 实现本地初始化、派生计算、全局设置与草稿提交边界；复用现有设置仓库。
3. 同步替换模型契约、解析、面板查值及运行快照，移除旧 CoC 请求和裁定分支。
4. 接入属性界面、结果卡片和 scoped 旧记录清理，删除对应废弃测试。
5. 完成必要验证后更新交付状态；未经验证不得标“已实现／已验收”。
