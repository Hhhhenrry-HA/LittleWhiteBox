# 变量 3.0

变量 3.0 把一张卡的玩法规则写进角色卡：有哪些数据、玩家能做什么、什么条件下发生什么，都由结算引擎按规则执行，模型只需要说“发生了什么”。从一个想法到一张能玩的卡，小白助手可以全程陪你做。还没决定用 2.0 还是 3.0，先看[变量系统总览](variables.md#选-20-还是-30)。

## 1. 从想法开始，不要求学习什么是3.0

你想做一张冒险卡：休息消耗补给，装备影响防御，委托完成后解锁商店。也许还没写下一个字，也没想好具体数值——把这个想法告诉小白助手，就能开始。

助手陪你把玩法补全：角色能做什么、需要什么条件、消耗什么、什么时候发生事件。然后在同一个卡片工作区里写角色设定、开场、世界书、变量开局值、规则和前端面板，接着检查规则、试算动作、按结果修改。试玩时发现问题，也回到这张卡继续改。

**助手就在酒馆里。** 它能直接看现场：读取聊天楼层里面板的实际 DOM 和 CSS 布局，翻插件日志，看你发来的截图，读当前聊天的真实变量，用当前进度试算一个动作。哪里显示错位、哪个按钮没反应、哪个数算得不对，它拿现场数据核对，再回到这张卡的草稿里改。这些不需要另外配置调试环境，打开助手就能用。

## 2. 写好一套玩法，多个地方直接使用

卡上的规则定义只写一份，同时用于：

- **更新模型**：可写字段、动作和参数直接生成提交工具，规则说明组装成更新资料；
- **正文模型**：世界书里的宏读出当前变量和相关玩法说明；
- **卡片面板**：商店、营地、装备界面上的按钮调用同一批动作，不必另写结算逻辑；
- **结算结果**：每处变化标明来自哪个动作、哪条规则。

作者改好一个动作，不需要再为更新模型另写一份协议、为正文另写一份说明、为面板另写一份计算。

卡规定“怎么玩”，聊天记录“玩到哪里”，详见[规则跟卡走，进度跟聊天走](#规则跟卡走进度跟聊天走)。

## 3. 复杂玩法由程序执行，模型不用逐项算账

剧情里买下并穿上一件盔甲，更新模型只需提交作者定义的“购买并装备”。扣钱、入库、换装、重算防御和负重、达到条件后的触发，都由结算引擎按卡上的规则完成。

动作可以带参数、前提和多个效果；属性可以由其他字段算出，越界自动修正；条件达成自动触发后续。表达式写不下的计算，用隔离运行的 JavaScript 函数写，比如战斗回合、多人按速度排序结算；掷骰则在“准备数据”时取得骰点，再交给规则计算。玩法越复杂，模型漏算、重算的机会就越少。好感度这类需要理解剧情的变化，仍可交给模型判断。

## 4. 关联修改作为一个完整事件处理

一次结算里的直接改值、动作、关联计算、规则修正和条件触发按顺序一起算完，再检查最终的结构和约束。全部通过才写入；任何一步不通过，整批都不生效。买东西要么扣钱和给物品一起成功，要么一起不生效，不会出现“钱扣了、货没到”。

结算前可以试算，结算后能看清、能补救、能撤销：

- **试算**：制作时，助手用当前进度把动作先算一遍，看会怎样变化，不改聊天进度。试算和游玩时的结算是同一个引擎，试出来的就是玩起来的。
- **失败原因**：比如“购买 · 条件不成立：现金 102，需要 ≥ 297”。
- **变化来源**：结果弹窗分开显示动作本身、关联计算、规则修正和触发，以及模型写的剧情原因。
- **重试保存**：变量已改但保存未确认时，只重新保存，不会再扣一次钱。
- **撤销与回滚**：每个回复版本记下实际变化，切换回复、删除末尾楼层或撤销时直接恢复，不重新请求 AI。

## 开始使用

### 1. 选择 3.0，启用卡上的规则

打开 **扩展设置 → 小白X → 数据互动 → 变量控制**，勾选 `变量管理`，下拉框选择 **`3.0 · 卡规则与结算`**，再点旁边的 `变量更新` 按钮。

- **角色卡已经带有 3.0 规则**：新建聊天时会自动初始化；已有聊天在“当前聊天”页点击“启用规则”。
- **角色卡还没有规则**：先到“制作规则”页制作，不能只把模式切到 3.0 就让普通卡自动拥有玩法。

初始化会补齐缺少的变量根，并按卡上规则计算和检查。例如卡使用 `hero`，聊天里还没有它，就从开局值创建；已经存在的 `hero` 会作为起点检查，不会直接换成开局值。其他独立变量不受影响。

### 2. 看这张卡何时更新

“当前聊天”页顶部会显示卡作者选择的方式：

| 卡的方式 | 游玩时怎么发生 |
| --- | --- |
| 回复前更新 | 发出玩家消息后先结算，再生成正文。自动执行，不需要另开开关。 |
| 回复后更新 | 读完正文再更新。勾“回复后自动更新”就自动执行，否则点 AI 楼下的“手动结算”。 |
| 回复前＋回复后更新 | 先确定这次行动的结果，正文写完后再处理作者分给后置的变化。 |

前后阶段各自调用更新模型，会产生各自的 API 费用。更新模型可选小白助手的主助手 API 或分身 API；API 在[小白助手](assistant.md)里配置。没有回复后更新的卡，不会显示后置开关或更新按钮。

### 3. 查看结果与保存状态

控制条只出现在最后一条玩家消息和最后一条 AI 回复下，具体取决于卡启用的更新阶段。两处共用“手动结算”“重新结算”“重试结算”等名称，状态标注“回复前／回复后”。“查看结果”打开弹窗查看变化、保存状态和失败原因；“设置”回到当前聊天的更新设置。执行中可以取消；保存失败时只需“重试保存”。

前置结果属于玩家发出的那条消息。停止正文、正文失败、重新生成或重新打开聊天，都复用已有的结果，不会重新掷骰、重复扣钱。改了最后一条玩家消息，楼下显示“消息已修改”，可以点“重新结算”。

**重新结算先真实回滚，再请求模型。** 重算玩家消息时，先撤销这条玩家消息及之后 AI 回复的变量变化，包括该范围内的面板操作，并确认保存；重算 AI 回复时，只撤销该回复及之后的变化。新请求失败或取消，就停在回滚后的状态，不恢复旧结果。回滚保存失败时先“重试保存”，不会继续发起模型请求。

回滚不删除正文，但被撤销的 AI 结算不再有效，需要按新前置结果重新生成回复并更新。该范围的其他回复版本也清除旧结算记录，切回它们不会复活已撤销的变量变化。在“查看结果”里点“撤销结算”只回滚，不请求模型；前置撤销后，下次生成不会偷偷补算。重新结算和撤销结算都会保留所选开场的开局值。

行动本身不满足条件，例如钱不够，会把失败原因交给正文演绎。请求失败或模型提交有误时，正文先停下来，玩家楼下提供“重试结算”和“跳过结算”。

**结算生效和保存成功是两件事。** 如果显示“结果已生效，但未确认保存”，当前变量已经改变，应点击“重试保存”。重试只保存已有结果，不会再次扣钱、发奖励或执行动作。

正常回复前结算会先把变量和记录交给酒馆，正文立即读取这些结果，随后随酒馆聊天一起保存，不在正文前额外等一次保存。手动操作、撤销和回复后更新仍会主动保存。

如果模型已经返回操作，只是本地计算环境故障，插件会自动再算一次，不重新请求模型。仍未完成时，点“重试结算”继续用这份操作计算；当前玩家消息尚无正文时，点酒馆“重新生成”也会复用它。只在当前页面保留这一笔待重试操作；成功、取消、切聊天，或消息、变量、规则变化后释放，刷新页面也会丢弃。

刷新或重新打开聊天后，如果玩家消息还没有前置结果，楼下会显示“未结算”，可以点“手动结算”重新请求更新模型，或“跳过结算”继续正文。已有的前置结果仍按原样复用。

## 制作自己的玩法

### 从玩法开始，而不是从一长串变量开始

先想清楚一次操作：什么条件下允许发生，发生后改变什么，能不能重复。例如“交付三份材料 → 完成委托 → 获得奖励 → 标记已领取”。再决定需要哪些字段。

变量适合保存**当前事实和玩法条件**：地点、资源、任务阶段、完成标记、次数、期限。剧情经过交给剧情总结，不必在变量里再存一份越来越长的事件日记。

**同一件事只存一处。** 能从别的数据推出来的值，比如“在哪个名单里”已经说明了人在哪，“当前有没有供电”已经说明了工作停没停，就交给计算规则算，不另存一个字段。另存一份，就要求每个动作都记得同步它；漏改一处时，结算照样成功，两个字段却互相矛盾，模型会把矛盾当成事实来写。

**每种资源都看一眼来路和去路。** 只消耗、补不回来的物资，只能占用、不能腾出的位置，攒了钱却没处花，玩家迟早会在剧情里去找缺的那一半。要么补上对应动作，要么在说明里写明剧情做不到，否则模型要么硬写、要么被拒。

“制作规则”页上方是三个主要操作：

1. **助手制卡**：把玩法告诉助手，由它编写规则、试算并修改。
2. **检查规则**：检查当前编辑内容并计算开局状态，显示开局变量或具体错误，不修改聊天。
3. **存入角色卡**：把规则、计算函数、工具和阶段脚本一起保存到卡上，之后的结算使用这套规则。

想自己改文件，展开“编辑规则源码”；改到一半可以先点“保存草稿”，草稿不会替换角色卡上的规则。

检查通过表示定义和开局状态可用，不代表每条玩法路线都已经验证。制作后还需要试一次成功、一次条件不满足，以及重复操作、换装或跨过时间点等实际场景。也试数量为 0、列表为空的情况，以及先改掉一个进行中过程依赖的条件、再让它继续。看试算结果时，要看所有变化的字段，不只看这次要测的那个：本该跟着变却没变，就是联动漏了，结果仍会显示成功。

### 规则文件里分别写什么

主文件是 `variables/definition.json`，自定义函数放在 `variables/functions/`，模型工具在 `variables/tools/`，阶段脚本在 `variables/scripts/`。这些是卡片工作区中的编辑文件，保存到角色卡后会随卡携带，不要求玩家安装同名本地文件。

| 内容 | 对应字段 | 用途 |
| --- | --- | --- |
| 何时更新 | `updates` | 回复前、回复后，或两者都用 |
| 变量结构与开局值 | `schema`、`initial`、`openings` | 有哪些数据、类型和范围，共用与各条开场的开局值；见[给每条开场设置开局值](#给每条开场设置开局值) |
| 字段含义与直接修改开关 | `access` | 是否允许直接改值，模型应依据什么剧情更新 |
| 玩家能做的操作 | `actions` | 动作名称、参数、前提和产生的变化 |
| 自动计算与修正 | `rules` | 算出属性，或把超出范围的值修正回来 |
| 条件达成后的变化 | `triggers` | 到达时间、阶段或次数后发生什么 |
| 不允许出现的状态 | `constraints` | 检查多个字段之间是否互相矛盾 |
| 自定义计算 | `functions` | 用 JavaScript 编写较复杂的计算 |
| 给正文看的信息分组 | `views` | 按场景选取人物、装备等相关说明 |
| 工具与阶段脚本 | `extensions` | 见下文[让助手制作扩展玩法](#让助手制作扩展玩法) |

变量使用 JSON 数据：文字、数字、布尔值、`null`、列表和对象。`initial` 的最外层是对象，各顶层字段对应原生聊天变量。3.0 首次启用时确定负责哪些顶层变量及其子字段；之后只在 `schema` 中增加声明，不会自动接管聊天里的其他独立变量。

动作的 `id` 用于程序提交，必填的 `title` 是结果和失败提示里显示的短名，`description` 是给模型看的完整说明。参数也可以写 `title`，让失败提示更容易看懂。

**动作只写一处。** 动作的 `effects` 写了扣钱，就按它扣钱，不必再到钱的字段里登记动作名。模型能用哪些动作来改变某个字段，由插件根据动作效果自动整理。

`access` 每项的 `direct` 是一个开关：`true` 允许模型直接改值，`false` 要通过作者写好的动作或规则改变。动作仍检查参数、阶段、前提和最终结果，钱不够照样不能花。

基准价、路程天数等永远不变的值，用现有的 `derive` 规则配固定的 `literal` 值；该值只写在规则里，不再重复放进 `initial`。计算规则负责的字段不能被动作或直接改值覆盖。

`updates` 必填。只选一个阶段时，动作和可直接修改的字段自动归到该阶段；同时选择 `before` 和 `after` 时，每个动作及允许 `direct` 的 `access` 项都需要写 `stages`。模型只拿到本阶段可提交的动作和字段，结算也按相同权限检查。**计算、修正、约束和触发只写一套，不分前后。**

选择阶段要看玩法需要，不是越多越好。掷骰、战斗、探索这类需要先知道结果再描写的完整行动适合放在回复前；依赖正文理解的关系变化适合回复后。若只是减一点血，通常直接放进已有动作或已有阶段，不值得为它单独多发一次请求。

完整的规则格式、营地示例（变量、动作、状态显示和面板按钮如何配合）以及卡片面板调用动作的接口，都内置在小白助手的制卡说明里。在“制作规则”页点“助手制卡”，直接问助手即可，例如“给我看营地示例的面板怎么调用动作”。

### 给每条开场设置开局值

可以直接告诉助手：“主开场从营地出发，带背包和 30 枚钱；第二条从港口出发，带船票和 80 枚钱。”

自己填写时，在“制作规则”展开“编辑规则源码”，选择 `variables/definition.json`：

- 共用的开局值放在 `initial`，各条开场不同的部分放在 `openings`。
- `openings` 按酒馆里左右切换开场白的顺序排列。主开场填好后，第 1 项对应主开场，第 2 项对应第一条备选开场，依次往后，也就是工作区里 `message/0.md`、`message/1.md`……的顺序。主开场留空时，酒馆会略过它，`openings` 就从第一条实际显示的开场开始排列。
- 每项只写这条开场要改的值，没写的字段沿用 `initial`。整条都一样就写 `{}`；没有对应项的开场也用共用值。
- 装备、同行者这类列表要写完整名单，会整份替换；写 `null` 也会替换原值。所有开场共用同一套变量结构和玩法规则。

下面只展示开局部分，放进原有的规则文件中，不是完整规则包：

```json
{
  "initial": {
    "hero": { "place": "营地", "coins": 30, "items": ["背包"] }
  },
  "openings": [
    {},
    { "hero": { "place": "港口", "coins": 80, "items": ["船票"] } }
  ]
}
```

调整开场白顺序时，也把 `openings` 的顺序一起调整。改好后点“检查规则”，再“存入角色卡”，新开测试聊天逐条切换，核对开场、面板和变量是否一致；再玩一轮并重开，确认进度保留。

### 面板读取与提交

同源聊天面板通过 `window.parent.LWB_StateV3` 访问 3.0。`await api.inspect()` 成功时，`result.state` 是已解析的当前状态对象；酒馆原生 `variables.local.get(root)` 返回存储值，对象根是 JSON 字符串。两者都读取当前聊天，不会自动选择面板所在楼的历史状态。

`await api.apply([{action:'动作ID', params:{}}])` 的第一个参数是操作数组；可选设置放在第二个参数。结果里的 `actions` 表示实际执行的动作，`changes` 表示实际变量差异；`ok:true` 只说明这批提交通过，不能证明玩家提到的所有意图都已被模型提交。

## 让助手制作扩展玩法

1. 在“制作规则”中点“助手制卡”，描述玩法，例如“行动前掷骰，成功后提示我”。助手选择合适的规则和脚本，编写并试算。
2. 在“扩展”中查看已有工具和三个脚本位置。需要调整就点“让助手修改”，需要验证就点“让助手测试”；不需要的功能可以停用。
3. 点“检查规则”，确认无误后“存入角色卡”。存卡后新开一个聊天，从开场完整试玩一轮，这样不会弄乱正在玩的进度。试玩出错后（不刷新页面），回到“制作规则”点“查看运行诊断”，再交给助手修。
4. 分享时导出角色卡，或在“规则包分享”中导出卡上已保存的规则包。工具和脚本一起携带；删除项会在下次存卡时移除。

- **模型工具**：更新模型按需调用，结果回到同一次对话；每次更新最多调用五次。最终提交成功就结束，提交失败最多纠正一次。没有工具的卡，每次更新只请求一次模型（提交有误时再纠正一次）。
- **准备数据**：在整批动作执行前取信息，读取的是批次起点状态，不能看到同批后续动作新建的对象。需要针对新对象准备数据时，先完成创建，再另批提交后续动作。纠错和本地计算重试复用已经取得的数据。
- **参与计算**：在普通操作后计算额外修改，再经过派生、修正、批次触发与最终检查；失败整批不生效。
- **结算成功后**：播放声音、通知面板等。附带操作失败会单独报告，变量仍已生效，正文继续。撤销、切换回复、重新打开聊天或重试保存不重复执行。

试算由小白助手构造输入、连续推演并检查结果，只计算，不调用酒馆或外部接口。“让助手测试”单项测试时会实际执行代码，运行前会确认；其中“结算成功后”脚本追加的结算只按正在编辑的规则试算，不写进聊天。要验证真正入账后的完整流程，就按上面第 3 步新开聊天试玩。

`checkDraft(draft, input, {state, stage, prepared})` 和 `tryDefinition` 都不会运行准备数据脚本，`prepared` 是试算者显式提供的模拟结果；单项 `testExtension` 只运行选定入口，不串起整个回合。它们通过不代表卡已发布或真实随机流程已通过。

玩家结果页只展示是否生效、变量变化和下一步。声音或通知失败不撤回已生效的变量，也不影响继续游戏；源码和单项重测放在制卡页的运行诊断中。

启用卡或开始更新前，会询问是否允许卡内代码操作酒馆和外部功能。选择“暂不允许”后，可到“当前聊天”再次点“启用规则”；已启用的聊天点“允许卡内扩展”，也可随时撤销。授权不随卡分享；会操作酒馆或其他插件的代码变化后重新确认，纯计算脚本不需要这项授权。

准备数据、工具结果与调试详情只保留在本次运行中。重新生成正文仍需知道的骰点等事实，由作者通过参数转换放进原有动作记录，或保存为真实游戏状态。

## 正文模型看什么，更新模型做什么

正文模型负责演绎，更新模型负责把剧情转成变量操作。两者需要知道同一套玩法事实，但不需要收到同样的操作指令。

启用回复前更新时，结算后的值先写入原生变量，本轮正文的世界书宏直接读到这些值。[剧情规划](ena-planner.md)的计划在玩家采用后才结算，再重新组装正文资料。

需要正文知道的前置结果会自动交给正文，不要求作者再放一个宏：

- 执行了动作，或变量有实际变化：交给正文；即使数值没变，已经执行的动作也会保留。
- 行动因条件不满足而未成立：把失败原因交给正文。
- 前置成功，但既没有动作也没有变量变化：不额外加入结算参考。跳过或撤销前置结算时也不加入。

这份参考只说明最新玩家消息中已经判定的部分，其余内容仍由正文演绎；前置没有变化，不代表正文发生后也没有变化。原始数据、字段路径和结果标签只是生成参考，不是要写进故事的内容。

前置记录会保存动作及其实际采用的完整参数，包括规则转换后的参数值。正文和回复后更新读取同一份已保存结果，知道做过什么、对谁做、用了多少，而不是只凭变量差异猜测；重新打开聊天或重新生成时也复用这份记录。

作者可以在正常启用的世界书条目中放入以下宏：

| 宏 | 展示内容 |
| --- | --- |
| `{{xbgetvar::hero.health}}` | 当前生命值；路径按自己的卡填写 |
| `{{xbgetvar::hero}}` | 整个 `hero` 对象的当前值 |
| `{{xbvardesc}}` | 卡中各视图的字段含义及相关玩法说明 |
| `{{xbvardesc::character}}` | 只展示 `views.character` 所涉及的说明 |

宏里的 `character` 只是举例的视图名，**不是固定关键字**。卡里定义了什么视图，就使用什么名字。启用聊天后，应把世界书实际使用的宏展开一次，确认读到的是这张卡的字段。

描述宏包含相关的动作、计算、触发和约束说明，但不包含当前值或提交指令。需要当前值时搭配取值宏使用，也可以按世界书条件只发送当前场景需要的部分。

规则里的数字和后果交给描述宏，角色设定和世界书写背景、人物和氛围。在设定里再手写一遍“每小时耗多少”“多久恶化一次”，改规则时它会停在旧值，正文模型就同时读到两个版本。反过来，写在自定义函数里、玩家能感受到的后果（恶化、花费、停工），也要写进对应动作或规则的说明；只写在代码里，结算照样发生，正文模型却不知道，可能写出相反的结果。

字段的 `description` 解释世界事实；`update` 解释什么时候更新、依据什么证据。后者只给更新模型。更新模型还会收到当前状态、结构要求、可写路径、动作参数和规则说明；它选择提交哪些变化，具体计算由引擎执行。

## 结算是怎样完成的

### 先计算和检查，再改变聊天

一次提交可以包含直接赋值 `set`、数值加减 `inc`、删除 `remove`，也可以包含卡上定义的动作。它们按顺序执行：前一项改过的值，会成为后一项的起点。`inc` 加减的是执行到这一步时的当前数字，不是本回合开始时的旧值；字段不存在或不是数字时会报错。

动作执行前会更新相关计算值，处理并检查参数，再检查前提。同一个动作中的多个效果读取同一份动作执行前状态，避免扣款顺序影响其他效果。动作执行后会再次计算、修正，并处理动作级触发；整批结束时处理批次级触发，最后检查完整状态。

表达式 `before` 和自定义函数的 `before(path)` 始终读取整批提交开始时的快照；`get` 读取当前执行位置的状态，包含同批前序动作的结果。

结构检查使用 **JSON Schema**，负责类型、必填字段和范围等要求；跨字段关系由 `constraints` 检查。规则负责计算与修正，校验器负责判断最终结果是否合法。所有修改先在临时状态中完成，通过后才写回聊天；失败或提交前取消不会写入一半结果。

这条流程用于 3.0 的模型更新和卡侧 API。直接在原生变量面板改值不等于执行玩法动作，不会自动补做对应奖励和触发。

### 较复杂的计算：隔离运行的 JavaScript

表达式不方便描述的逻辑可以写成自定义函数，在隔离环境里运行。函数通过声明的路径读取数据，也可以读取本批修改前的值；不能访问酒馆页面、网络或存储。

这样，试算可以执行同样的计算，而不会顺手发送请求或改动页面。同一次结算复用计算线程，但每次函数调用的运行环境独立。函数以计算量和内存限制防止失控，触发链检查循环并设轮数上限；后台暂停或结果送达较慢不会被当成规则超时。取消或计算失败时，整批修改不生效。

普通比较条件失败时，结果可以显示字段名、实际值和要求值。自定义函数内部的判断不会被自动拆解，玩家看到动作当前不能执行；函数名、函数说明及异常详情保留在制卡页的运行诊断中。

## 切换回复、撤销与存档

### 恢复已有结果，不重新演一遍玩法

每个已结算的回复版本（swipe）保存自己的变化记录；前置记录保存在玩家楼。切换已有版本、从某楼删除到末尾或撤销结算时，3.0 根据记录恢复变量，不重新请求 AI，也不重新执行动作和奖励。取消正在生成的新版本时，会恢复原版本的变量。单独删除中间楼、隐藏或移动楼层不自动改写变量。

如果保留后面的楼层，只切换前面某一楼，后面已经结算的字段结果仍会保留，**不会按改写后的剧情重新推演后文**。例如后面已经开门，前面却换成了没拿钥匙的版本，恢复后就可能出现矛盾。

历史切换后会检查字段格式和卡上约束。没有冲突就不打扰；有冲突则显示规则和当前值，例如“开门必须持有钥匙：钥匙为无，门为已打开”。切换本身不会被阻止，程序也不会替玩家决定关门还是补钥匙。可以切回原版本，或通过后续操作解决冲突；下一批修改只要最终合法就能生效。

### 规则跟卡走，进度跟聊天走

- **角色卡**保存规则、计算函数、工具和阶段脚本，随卡导出、分享。
- **聊天**保存当前变量（就是酒馆原生的聊天变量），3.0 另存恢复所需的变化记录。重新打开聊天使用已保存的进度，不重新开局。
- **导入／导出规则**包含 `definition`、`functions` 及配置的 `tools`、`scripts`，不是聊天存档。导入会先检查、再确认，完整替换卡上的规则和源码，不清空当前变量，也不丢弃编辑草稿。已有草稿需重新读取卡上内容后再合并保存。

正在等待的模型更新如果遇到聊天、回复、当前变量或卡上规则变化，不会把旧结果覆盖到新状态上。结果已生效但保存未确认时，界面会单独提示重试保存。

## 常见问题

### 正文已经写了结果，还会和变量不一样吗？

回复后更新不会回头改写已完成的正文。需要先确定数值再描写的玩法，可以由作者选择回复前更新，也可以由卡片按钮先执行动作，再把实际结果交给正文。正文拿到实际结果后仍由模型演绎，因此试玩时要核对叙述与结果是否一致。

### 保存新规则，会重置当前进度吗？

不会。之后的结算使用新规则，但保存规则本身不会重新计算现有进度，也不会重算历史楼层。因此，修改公式后，面板上的旧计算值可能保留到下一次结算；不要把“规则已保存”理解成“当前状态已按新规则全部更新”。

### 不同开场可以设置不同的初始值吗？

可以。按[给每条开场设置开局值](#给每条开场设置开局值)配置，也可以直接告诉助手每条开场要从什么状态开始。

### 支持群聊吗？

当前 3.0 按单张角色卡管理规则，尚不支持群聊。

### 需要让正文模型输出变量代码吗？

不需要。3.0 通过插件更新或卡侧 API 修改变量，不从聊天正文执行提交代码。正文可以专注叙事，无需插入专用的变量提交块。
